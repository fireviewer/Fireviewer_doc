# FireViewer — Fire Evolution Timeline

## Purpose

FireViewer represents wildfire evolution as a sequence of **time-bounded, provenance-aware states** attached to a stable spatial reference.

The objective is to document how the available evidence changes over time without converting missing information into invented geometry.

## Core rule

```text
observed ≠ reconstructed ≠ interpolated ≠ simulated ≠ predicted
```

These categories may coexist in a study, but they must remain distinguishable in contracts, storage, visualisation and downstream datasets.

## Why this matters

A wildfire is not observed continuously from every location. Real incident data contains gaps:

- satellite passes are discrete;
- ground photographs are local and intermittent;
- public reports may describe sectors rather than exact contours;
- smoke can obscure the active front;
- burned-area products can be produced after the active phase;
- retrospective maps can improve the final understanding of the incident.

If a system silently draws a smooth line through those gaps, it creates information that was never actually observed.

FireViewer instead preserves the uncertainty and temporal resolution of the source material.

## Temporal state families

### Observed state

An `observed` state is derived from a source that directly supports the represented geometry at a documented time or time interval.

The exact admissibility rules depend on the source type and review contract. The label does not mean "perfect truth"; it means the state is represented as an observation rather than a reconstruction or simulation.

### Human-reviewed interpretation

Some evidence may support an interpretation that is useful but not equivalent to a directly observed perimeter. These layers keep their own semantic identity and references to the evidence and decision that created them.

### Retrospective reconstruction

A `reconstructed` state is produced after the fact from a combination of available evidence such as area reports, sectors, maps, remote-sensing products or reviewed observations.

A reconstruction can be scientifically useful while still being distinct from what was known at the time.

### Simulation

A `simulated` state is generated by a model or scenario engine. It is never inserted into the observed timeline as if it were evidence.

### Prediction

FireViewer core is not a wildfire forecasting product. A future predictive experiment, if one exists, must remain a separate product or research layer with explicit model provenance and must not contaminate the observation timeline.

## Unknown intervals

When two accepted states occur at `T1` and `T2`, FireViewer does not assume that the perimeter evolved linearly between them.

```text
T1                 T2
│                   │
observed A           observed B
│                   │
└──── unknown ───────┘
```

The canonical value between observations is therefore allowed to be **undefined**.

A derived animation may visually transition between frames for presentation purposes, but that rendering choice must not be stored or exported as an observed intermediate geometry.

## Relationship to the map build

Temporal fire states reference a specific immutable spatial build.

```text
map_build_A
   │
   ├── state T1
   ├── state T2
   ├── state T3
   └── reconstructed state R1
```

This prevents a later terrain update from silently changing the reference geometry used by the historical timeline.

A new temporal state does not require a new terrain build unless the spatial reference itself must change for a documented reason.

## Current perimeter package

The spatial pipeline can normalise a JSON/GeoJSON perimeter representation to `EPSG:2154` and produce artifacts such as:

```text
geographic-perimeters.usda
fire-progression-timeline.json
perimeters.normalized.json
perimeter-layer.manifest.json
preview/perimeter-viewer.manifest.json
preview/frame-*.glb
```

The OpenUSD layer, normalised geometry and timeline are the reference artifacts. Browser-oriented GLB files are derived views.

## Timeline entry requirements

A timeline entry should be able to answer:

- what semantic class is this state?
- what time or interval does it describe?
- what source or evidence supports it?
- what map build does it reference?
- what CRS was the original geometry supplied in?
- what transformations were applied?
- was the state human-reviewed?
- what is the confidence or uncertainty representation?
- what version of the temporal contract produced it?

If these questions cannot be answered, the state is not suitable for a reproducible FireViewer timeline.

## Public presentation

The public interface should make category boundaries understandable without requiring the user to understand the complete internal contract vocabulary.

At minimum, the interface must avoid visually implying that:

- a reconstructed perimeter was observed live;
- an uncertain zone is an exact front;
- a burned area is an active-fire perimeter;
- a simulation is the observed future of the incident;
- an unknown time interval contains a known progression.

Textual fallback remains important because colour and animation alone are not sufficient to communicate these distinctions reliably.

## Retrospective packs

Historical FireViewer reconstruction packs can use time windows when direct geometry is unavailable, provided that:

- the geometry is marked `reconstructed`;
- the time window is explicit;
- supporting source references are preserved;
- the method is documented;
- quality checks do not get reinterpreted as proof that the geometry is an official perimeter.

A retrospective dataset and an observed-perimeter package are different product families.

## Research value

A well-formed timeline allows several post-event questions to be studied reproducibly:

- how quickly did independent sources converge on the final documented extent?
- which observation types added useful spatial information?
- where did AI localisation abstain or fail?
- how did uncertainty change as new evidence arrived?
- how different is a retrospective reconstruction from what was known at the time?
- which time windows remain poorly documented?

These questions are one of the main reasons FireViewer preserves temporal provenance rather than only the final perimeter.

## Non-goals

This timeline is not intended to:

- generate a continuous fire-spread forecast;
- fill observation gaps automatically;
- certify an official perimeter;
- infer emergency-response decisions;
- provide evacuation or tactical guidance.
